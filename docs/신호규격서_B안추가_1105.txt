0. 왜 B안이 필요한가
----------------------------------------------------------------
 - 보드의 USB 사운드카드를 Android 앱에서 쓰면 소리가 나지 않는다
   (퀄컴 USB 오디오 오프로드 문제로 추정, 10/30 조사)
 - A안: 보드에서 root 권한으로 tinycap(녹음)·tinyplay(재생)을 직접 부른다
 - B안: 자녀 앱(폰)이 녹음하고 재생한다. 보드는 STT·판단·LLM·TTS만 한다
   → AI는 그대로 보드 안에서 돈다(온디바이스 유지). 폰은 마이크·스피커 역할만 한다

 11/5 확인: 보드 안 STT·TTS가 wav 파일로 한 바퀴 돈다
   wav 입력 → STT → 판단 → 공감 한마디 → TTS wav, 걸린 시간 0.7~1.2초
   B안은 이 흐름 앞뒤에 "폰이 wav를 보내고, 받은 wav를 튼다"만 붙이면 된다


1. 바뀌는 것 한눈에
----------------------------------------------------------------
 - 연결 방식, start/stop, 신호 8종, 신호 순서, 화면 규칙은 v1.0 그대로
 - 앱 → 디바이스에 2종 추가: audio(녹음 보내기), played(재생 끝 알리기)
 - 디바이스 → 앱 신호 4종(empathy, playing, not_found, safety)에 audio 값 추가
 - 소리는 JSON 안에 base64 글자로 넣는다(바이너리 프레임 쓰지 않음)
 - 앱이 B안을 쓴다는 것은 start에 "mic": "app"을 넣어 알린다
   (넣지 않으면 v1.0처럼 보드가 마이크·스피커를 쓰는 것으로 본다)


2. 앱 → 디바이스 (v1.0 2종 + 추가 2종)
----------------------------------------------------------------
 ID     type    함께 보내는 값                         언제
 -----  ------  -------------------------------------  ---------------------------
 AB-01  start   mic: "app"  (B안일 때만)                "온기에게 말하기"를 눌렀을 때
 AB-02  stop    없음                                   멈춤을 눌렀을 때 (v1.0 그대로)
 AB-11  audio   format: "wav"                          아이 말이 끝났을 때
                data: 녹음 wav를 base64로 바꾼 글
 AB-12  played  stage: "empathy" / "message" / "notice" 받은 소리를 다 틀었을 때

 예)
 {"type": "start", "mic": "app"}
 {"type": "audio", "format": "wav", "data": "UklGRiQAAABXQVZF..."}
 {"type": "played", "stage": "empathy"}

 녹음 형식 (AB-11)
 - wav, 16비트, 모노, 16000Hz (다른 샘플레이트도 받지만 16000Hz를 권장)
 - 최대 10초. 10초가 되면 앱이 녹음을 끝내고 보낸다
 - 말 끝 판단: 앱의 "다 말했어" 버튼 또는 1.5초 동안 조용하면 끝 (둘 중 먼저)
 - listening을 받은 뒤에 녹음을 시작하고, 녹음이 끝나면 audio를 보낸다

 played (AB-12)
 - 디바이스는 소리를 보낸 뒤 played를 기다렸다가 다음 신호를 보낸다
 - stage는 지금 끝난 소리: empathy(공감 한마디) / message(부모 메시지) /
   notice(받아주는 말·안전 응답)
 - 디바이스는 played가 오지 않아도 (소리 길이 + 3초)가 지나면 다음으로 넘어간다


3. 디바이스 → 앱 (v1.0 8종, 4종에 audio 추가)
----------------------------------------------------------------
 ID     type       추가되는 값 (B안일 때만)
 -----  ---------  --------------------------------------------------------
 AB-05  empathy    audio: 공감 한마디 소리 (wav base64, 22050Hz 모노)
 AB-06  playing    audio: 부모 메시지 소리
                     kind=voice → 부모 녹음 파일 그대로 (m4a base64)
                     kind=text  → 글을 온기 목소리로 읽은 소리 (wav base64)
                   audio_format: "m4a" / "wav"
 AB-07  not_found  audio: 받아주는 말 소리 (wav base64)
 AB-10  safety     audio: 안전 응답 소리 (wav base64)

 - listening, thinking, idle, error는 v1.0 그대로 (소리 없음)
 - audio가 없는 경우(TTS 실패 등)에는 글만 보여 주고 바로 played를 보낸다

 예)
 {"type": "empathy", "text": "친구랑 싸워서 속상했구나", "has_message": true,
  "author": "mom", "audio": "UklGRi..."}
 {"type": "playing", "situation_id": 4, "message_id": 1, "author": "mom",
  "kind": "voice", "text": null, "audio_format": "m4a", "audio": "AAAAGGZ0eXBN..."}


4. 신호 순서 (B안)
----------------------------------------------------------------
 v1.0 4장 순서는 그대로이고, 사이에 앱의 audio·played가 끼어든다.

 ① 부모 메시지 재생
   앱 start(mic=app) → 보드 listening → [앱 녹음] → 앱 audio
   → 보드 thinking → 보드 empathy(audio) → [앱 재생] → 앱 played(empathy)
   → 보드 playing(audio) → [앱 재생] → 앱 played(message) → 보드 idle

 ② 공감 한마디만
   ... → 보드 empathy(has_message=false, audio) → [앱 재생] → 앱 played(empathy) → 보드 idle

 ③ 맞는 메시지 없음
   ... → 보드 not_found(audio) → [앱 재생] → 앱 played(notice) → 보드 idle

 ④ 위기 표현
   ... → 보드 safety(audio) → [앱 재생] → 앱 played(notice) → 보드 idle

 ⑤ 오류
   - listening 뒤 10초 안에 audio가 안 오면: 보드 error(D-001) → idle
   - 받아쓴 글이 비어 있으면: 보드 error(D-002) → idle

 ⑥ 중간에 멈춤: 언제든 앱 stop → 앱은 재생을 멈추고, 보드는 idle (v1.0 그대로)


5. 시간 (11/5 보드 측정, wav 시연 문장 4개)
----------------------------------------------------------------
 단계                          걸린 시간
 ----------------------------  -----------------------------
 STT (SenseVoice)              0.16 ~ 0.20초
 판단 + LLM (지금은 가짜)      약 0.31초 (진짜 LLM은 0.65~0.77초)
 공감 TTS                      0.24 ~ 0.40초
 합계 (말 끝 → 공감 소리 준비)  0.71 ~ 0.87초  (목표 3초 이내)

 B안에서 더해지는 시간: 녹음 전송(약 150KB) + 공감 소리 전송(약 100KB).
 같은 공유기 안이면 0.1초 안쪽으로 본다(11/11에 측정).


6. 앱(유정) 할 일 (B안으로 정해지면)
----------------------------------------------------------------
 1. start에 "mic": "app" 넣기
 2. listening을 받으면 녹음 시작 → "다 말했어" 또는 1.5초 조용 또는 10초 → wav(16kHz 모노) → base64 → audio
 3. empathy / playing / not_found / safety에 audio가 있으면 base64를 풀어 재생
    (playing은 audio_format이 m4a일 수 있음)
 4. 재생이 끝나면 played(stage) 보내기
 5. stop을 누르면 재생 멈추고 stop 보내기
 추천 패키지: 녹음 record, 재생 just_audio 또는 audioplayers (둘 다 wav·m4a 됨)
 권한: 마이크 권한(RECORD_AUDIO / NSMicrophoneUsageDescription)


7. 디바이스(지현) 할 일 (B안으로 정해지면)
----------------------------------------------------------------
 1. SignalServer: start의 mic, audio, played 받기
 2. OngiFlow.listen: mic=app이면 audio를 기다렸다가(10초) ai.stt(wav)
 3. 공감·받아주는 말·안전 응답: TTS wav를 base64로 신호에 넣기 (지금 TTS 코드 그대로)
 4. 부모 메시지: voice는 받아 둔 m4a를 그대로, text는 TTS wav
 5. 고정 시간 대신 played를 기다리기 (소리 길이 + 3초 넘으면 넘어감)
 6. 시험: test_client.py에 wav 파일을 audio로 보내는 기능 추가
 예상 시간: 2~3시간 (STT·TTS는 11/5에 이미 붙음)


8. A안과 비교 (11/11 결정용)
----------------------------------------------------------------
            A안 (보드 tinyalsa)                B안 (폰이 마이크·스피커)
 ---------  ---------------------------------  ---------------------------------
 온기 모습  보드 스피커에서 소리 (원래 설계)   폰에서 소리
 AI 위치    보드                               보드 (같음)
 위험       root 권한·카드 번호·사운드카드     앱 쪽 일이 늘어남(녹음·재생)
            전원 순서에 따라 깨질 수 있음      폰 마이크라 소리는 안정적
 할 일      도우미 + 녹음·재생 연결            앱 녹음·재생 + 신호 4종 수정
 시연 위험  사운드카드가 안 되면 시연 불가     폰만 있으면 됨

       B안 디바이스 쪽은 STT·TTS가 이미 되므로 2~3시간이면 붙는다.
